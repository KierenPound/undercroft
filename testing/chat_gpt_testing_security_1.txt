## CRITICAL — confirmed live, right now

**Anonymous internet users can read your pending invite codes.**

With nothing but the public anon key — no login, no session — the REST API returned your pending invitations:

```
[anon estate_access pending] HTTP 200  rows=2
   -> role=executor invite_code=3G****  estate_id=58907709…
   -> role=owner    invite_code=38****  estate_id=58907709…
[anon estates]              HTTP 200  rows=0     <- isolation works here
```

Cause: the fourth clause of `estate_access_select_linked` tests only the *row*, not the requester, and the policy is granted to `anon`:

```sql
OR (status = 'pending' AND user_id IS NULL AND invite_code IS NOT NULL)
```

Combined with `GRANT SELECT ON public.estate_access TO anon`, every outstanding invite code is world-readable. Since anyone who knows a code can claim it, **an unauthenticated stranger can turn an outstanding co-owner invite into full access to your estate.**

**Recommendation: revoke the two outstanding invites now** and re-issue fresh ones once the fix below is in. Treat both codes as compromised. (I've masked them above rather than reproducing them.)

## Second finding — needs a staging check

`recreate_all_tables.sql` permits any signed-in user to grant themselves access to **any** estate:

```sql
CREATE POLICY estate_access_owner_insert ON public.estate_access
    WITH CHECK ( user_id = auth.uid() OR public.is_estate_owner(estate_id) );
```

The `user_id = auth.uid()` branch passes with no requirement that the estate belongs to you and no invite involved. A signed-in user can POST an `estate_access` row `{estate_id: <any estate>, user_id: <themselves>, role: 'owner', status: 'accepted'}` and become an accepted co-owner. Estate UUIDs aren't secret, because of the finding above.

Two caveats, stated honestly:
- I could not test this live (it would write a real row).
- [0001_fix_estate_access_rls_recursion.sql](file:///Users/kierenpound/Developer/UnderCroft/supabase/migrations/0001_fix_estate_access_rls_recursion.sql#L73-L79) contains a **different, safe** version of the same policy (`estate_id IN (SELECT id FROM estates WHERE owner_id = auth.uid())`). The two files disagree, so which one is live in your project is unverified. Either way the drift is a problem — [recreate_all_tables.sql](file:///Users/kierenpound/Developer/UnderCroft/supabase/recreate_all_tables.sql#L703-L708) is the newer, consolidated script, and it's the permissive one.

## Third finding — the invite code is not a secret at the database layer

The claim policies check that a row *is* pending, but never check that the code the caller typed matches it. RLS can't compare against client input, so the only real check is the app's `.eq('invite_code', code)` — a client-side filter, and the code is itself readable (finding 1). The UPDATE is then keyed on the row id:

[onboarding_view.dart](file:///Users/kierenpound/Developer/UnderCroft/lib/views/onboarding_view.dart#L136-L152) selects by code, then updates `.eq('id', ...)` setting `user_id`/`status`. The guard trigger from 0019 correctly stops the *role/estate* being altered, but nothing stops a caller skipping the SELECT and updating any pending row directly.
